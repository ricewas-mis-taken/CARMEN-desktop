CARMEN FOCUS — DESIGN DECISIONS LOG
=====================================
An append-only record of real architectural/design choices for this app --
not bug fixes, not routine implementation detail. A "design decision" here
means: there were at least two genuinely different ways to do something,
one was picked deliberately, and future-you (or future-me) would otherwise
have to re-derive the reasoning from scratch or accidentally re-litigate it.

Add a new dated entry every time a decision like that gets made -- see
FEATURE_IMPLEMENT.txt's own checklist, which has a step reminding to update
this file for exactly that reason. Newest entries go at the bottom.

Format per entry:
  [YYYY-MM-DD] Short title
  Decision: what was chosen.
  Why: the reasoning / what alternative was rejected and why.
  Scope: what this does and doesn't apply to, if not obvious.

-------------------------------------------------------------------------

[2026-09-25] Edit Task vs Edit Session Rules are two deliberately different tools
Decision: Editing a Task's rules (qt_ui/task_editor.py) always updates the
task's own stored template AND, if that exact task's own session is the one
currently running (session_manager.get_status()'s source/eventId matches),
applies the change live too. "Edit Session Rules" (qt_ui/picker_dialogs.py)
only ever touches the live session, never persists to any template.
Why: these solve different problems -- "I want this task's rules different
from now on" vs "just for this one session, do something different" -- and
collapsing them into one tool would force a false choice every time either
is used.
Scope: the live-apply check matches on source in ("task", "review") --
a review timer linked to this task also carries its eventId (see the entry
below), so editing/deleting the task must recognize that case too, not
just plain source == "task".

[2026-09-25] Deleting a task ends its own currently-running session
Decision: qt_ui/task_editor.py's delete flow checks the same source/eventId
match as the live-edit path above, and calls session_manager.end_session()
first if this exact task is what's running.
Why: leaving an enforcement session running against a task that no longer
exists is a worse default than ending it -- there's nothing left to point
the session's UI/history at.
Scope: only the exact task whose own session is running gets ended;
editing/deleting an unrelated task never touches a different task's live
session.

[2026-09-25] The local API server must run threaded
Decision: api_server.py's app.run() uses threaded=True.
Why: confirmed live -- without it, Werkzeug's single-worker dev server lets
one wedged/slow request permanently block every other request forever,
including trivial ones with no I/O of their own (GET /health). This isn't
a performance tweak, it's a correctness requirement: this API has multiple
concurrent pollers (the extension's background.js, the Qt UI, the popup)
that must never be able to starve each other.

[2026-09-25] apiFetch (extension) must always resolve in bounded time
Decision: chrome/background.js and firefox/background.js's apiFetch()
wraps its fetch() call in a 5-second AbortController timeout.
Why: fetch() has no default timeout. Paired with the desktop-threading
decision above, a wedged desktop app used to hang every single extension
call forever instead of ever reaching the existing "desktop unreachable"
fallback -- the fallback code was already correct, it just never got a
chance to run.

[2026-09-25] A review timer is independent of session_manager's one active session
Decision: review_store.py's review-in-progress tracking (_active_sessions)
stays completely separate from session_manager._state. Starting a review
while a different session (e.g. a pomodoro/task session) is already active
does NOT create a second session_manager session and does NOT touch the
existing one in any way -- it just times independently in the desktop UI's
own review banner. Ending either one never affects the other.
Why: session_manager is a single-session model by design (one endTime, one
lockMode, one blocklist at a time) -- making it support two truly
overlapping sessions with independent enforcement rules would be a much
larger, riskier rearchitecture for a need that's actually already served
by keeping review timing as its own separate concept.
Rejected alternative: a stack/queue of concurrent session_manager sessions
with priority-based enforcement. Not implemented -- the enforcement rules
in effect are still whichever single session_manager session is actually
active, if any; a review never overrides or suspends it.

[2026-09-25] "Review has priority" means display priority, not enforcement priority
Decision: GET /status gains a reviewInProgress field, populated from
review_store.get_active_review() independent of whatever session_manager
reports as the active session (deduped only when it's literally the same
review driving that session, to avoid showing it twice). The extension
renders this as an always-visible banner above whichever main view (setup
or active-session) the popup is otherwise showing, and keeps polling alive
for it even when no other session is active.
Why: this was the direct, minimal fix for a real bug -- a review started
alongside an unrelated session (e.g. a pomodoro) was completely invisible
to the extension, and cancelling that unrelated session made the popup
show nothing at all even though the review was still legitimately running
in the desktop app. "Review should have priority over the pomodoro" was
interpreted as "the review must always be visible, prominently, regardless
of what else is or isn't happening" -- not as "the review's rules should
override the other session's lock mode/blocklist," which the previous
entry's decision explicitly keeps separate.
Scope: this only affects display. It does not change which
lockMode/processBlocklist/domainWhitelist is actually enforced at any
given moment -- that's still governed entirely by whichever single
session session_manager reports active, per the entry above.

[2026-09-25] An independent review's pause state lives in review_store, not the Qt widget
Decision: review_store.py's _active_sessions entries now carry their own
pause bookkeeping (accumulated_seconds/resumed_at/auto_paused), with
pause_active_review()/resume_active_review()/auto_pause_for_break()/
auto_resume_from_break() as the only ways to change it. qt_ui/review_tab.py's
_ReviewBanner delegates to these for any review with a real review_store
token (_is_independent_review()) instead of using its own local
_is_paused/_accumulated_seconds fields, which it still uses unchanged for
the one case that has no review_store token at all (the first-attempt flow,
timing a problem that doesn't exist in the DB yet).
Why: a pomodoro's break phase needed to auto-pause a review running
alongside it (see session_manager._advance_pomodoro_locked), and the
extension needed to both see that pause state and let the user manually
undo it. Neither is reachable if pause state only lives on a QWidget
instance that may not even be constructed at the time (the desktop UI
doesn't have to be on the Review tab, or open at all) -- it has to live
in the same place get_active_review() already reads from.
Scope: this does NOT apply to a review driving session_manager's own
session (end_session_on_finish=True) -- that one already deferred to
session_manager.pause_session()/get_status()["isPaused"] as its source of
truth, unchanged.

[2026-09-28] Violation-cooldown dedup lives in a shared choke point, not in record_violation() itself
Decision: window_tracker.py's ~1.5s poll loop and enforcer.py's instant
WinEvent hook (_on_foreground_changed) used to keep two entirely separate,
unshared cooldown trackers before calling session_manager.record_violation()
-- window_tracker's own process-name-keyed dict, enforcer's own hwnd-keyed
one. Under timing skew (the instant hook reacts the moment Windows reports a
foreground change; the poll loop's own tick can have already sampled that
same foreground window a moment earlier), the same physical "switched to a
blocked app" event could get recorded by both, double-counting one real
violation. Fixed by adding enforcer.record_violation_deduped(process_name)
-- a single shared, lock-guarded, process-name-keyed cooldown registry used
by every real call site in both files -- and routing all of them through it
instead of calling session_manager.record_violation() directly.
Why: the alternative considered was moving the dedup into
session_manager.record_violation() itself, so it would be impossible to
double-count no matter who calls it or how. Rejected: record_violation()
already has direct callers (this codebase's own test suite included) that
legitimately need to log two genuinely distinct violations back-to-back with
no gap -- e.g. tests/test_enforcer.py calls it twice in a row to reach
violationCount==2 for message-formatting coverage, with no real event
separating them. A blanket cooldown inside record_violation() itself would
have silently swallowed the second one, turning a "log one violation"
primitive into something with an opinion about timing that not every caller
wants. Keeping the dedup in a wrapper both real (non-test) callers route
through instead means record_violation() stays a plain, unconditional
primitive, while the actual production risk (two different code paths
guessing independently about the same physical event) is fixed at the one
place that's actually about recognizing "these two calls are almost
certainly reports of the same event."
Scope: only affects whether a violation gets logged/counted
(session_manager.record_violation()). Does not gate any enforcement action
itself (minimize, redirect, overlay) -- those keep their own existing,
independent cooldowns/dedup (HARD_REDIRECT_COOLDOWN_SECONDS, is_new_flag,
_show_violation_notice's own _last_violation_notice, etc.), unchanged.

[2026-09-29] tasks_store.add_domains_to_whitelist() replaces get_task()+update_task() for the domain-whitelist-add route
Decision: a red-team pass found api_server.py's task_domain_whitelist_add
route did get_task() (lock, read, release), merged the new domains into
the list in plain Python with no lock held, then update_task() (lock,
write, release) -- two separate lock acquisitions around an unlocked
read-modify-write. Two concurrent adds of different domains to the same
task both reported 200 success, but whichever update_task() call landed
last silently discarded the other's domain. Fixed by adding
tasks_store.add_domains_to_whitelist(task_id, domains), which does the
whole read-merge-write inside one _lock acquisition (tasks_store's _lock
is an RLock, so this nests safely the same way update_task()/delete_task()
already read/write load_tasks()/save_tasks() under _lock directly rather
than calling other locked functions).
Why: matches the shape session_manager.add_domain_to_whitelist()/
remove_process_from_blocklist() already correctly use for the same kind of
merge-into-a-list operation -- any read-modify-write that needs to be
atomic belongs inside a single lock acquisition as its own named
operation, not composed from two already-locked functions with a gap
between them.

[2026-09-29] POST /review/problems/<id>/finish verifies the token's problem_id before committing, and forwards self_solved/shakiness/duration_seconds
Decision: a red-team pass found two bugs in this one route. First,
review_store.finish_review(session_token) was called -- which commits its
side effects (logs the review_sessions row, bumps review_count/
last_reviewed_at, reschedules the problem) immediately -- BEFORE the route
checked whether the token's own problem_id matched the URL's problem_id.
A token sent to the wrong problem's finish URL got silently recorded
against the CORRECT problem while the client was told 409 "doesn't belong
to this problem," with the token now permanently burned and no way to
retry. Second, the route never read self_solved/shakiness/duration_seconds
out of the request body at all, despite finish_review()'s real signature
accepting all three -- every review finished over HTTP was unconditionally
logged as solved, shakiness 3, regardless of what the client actually sent.
Fixed both: added review_store.peek_active_review_problem_id(), which
looks up a token's problem_id without consuming it, so the route can
verify the match BEFORE calling finish_review() at all; and added real
validation + forwarding of self_solved (bool)/shakiness (int 1-5)/
duration_seconds (non-negative int) from the request body.
Why: any check that gates a commit has to run before the commit, not
after -- checking the returned value's shape after the side effects
already happened can only ever confirm-after-the-fact, never actually
prevent the wrong commit from happening in the first place.

[2026-09-29] start_review()'s existence check is re-run inside the same lock that does the insert
Decision: a red-team pass found a TOCTOU race between start_review()'s
existence check (run before _lock is ever taken) and delete_topic() -- if
delete_topic() runs in the gap between that check and the insert, it finds
nothing yet in _active_sessions to evict (this thread hasn't inserted its
entry yet), then start_review() goes on to insert an entry for the
now-deleted problem anyway. That orphaned entry permanently jams the
one-review-at-a-time guard added earlier this session (start_review()
refuses to start anything new while _active_sessions is non-empty), with
no way to clear it short of a process restart.
Fixed by re-running the existence check a second time, inside the same
`with _lock:` section that does the insert. Since get_problem() itself
takes _lock (and _lock is a plain, non-reentrant threading.Lock), the
re-check can't just call get_problem() again without deadlocking -- it
queries the connection directly instead, the same way delete_topic()
already reads from the DB while holding _lock.
Why: any TOCTOU fix has to make the check and the action it gates atomic
with each other, not just serialize the containing dict access (which was
already correctly locked before this fix) -- the race lived in the gap
before the lock was ever acquired, not in the locked section itself.

[2026-09-29] _is_string_list() caps list size and entry length, applied to every route that reuses it
Decision: a red-team pass found POST /session/start accepted a
2,000,000-entry process_blocklist with no complaint, bloating
session_state.json to 44.7MB and making every subsequent violation-tick
rewrite of that file (done from scratch on every violation) take ~0.6s.
Fixed by adding _MAX_LIST_ENTRIES (2000) and _MAX_ENTRY_LENGTH (500) caps
directly inside the shared _is_string_list() validator, rather than only
at the one route that was actually attacked -- that same helper is reused
by /session/update, the config blocklist/whitelist routes, and
/focus/rules's whitelist check, all of which had the identical unbounded
gap.
Why: fixing this at the shared validator instead of duplicating a
length check at each call site means no future route that reuses
_is_string_list() can reintroduce this class of bug by omission.
Scope: 2000 entries / 500 chars per entry is a generous multiple of what a
real hand-built blocklist or whitelist would ever need -- picked to be
obviously above any real usage, not a tight fit.

[2026-10-04] "Start First Attempt" is exposed to /status via a published snapshot
Decision: the first-attempt banner (qt_ui/review_tab.py) publishes an
in-memory snapshot to review_store (publish_first_attempt, every 1s tick;
cleared on finish/end/external end) and GET /status falls back to it for
reviewInProgress when no real review is being timed, flagged isFirstAttempt
with problemName "First attempt". Snapshots not re-published for 10s read as
gone. The extension can view it but not pause/resume it (the banner owns
that state).
Why: a first attempt has no problem row, so no _active_sessions entry, so it
was invisible to the extension whenever another session (e.g. a pomodoro)
was active.
Rejected alternative: a placeholder _active_sessions entry. Not used --
those are keyed to real problems and get_active_review()'s other callers
(restart recovery, independent-review pause) would misread it.
Cross-reference: carmen-extension DESIGN_DECISIONS.txt [2026-10-04].

[2026-10-04] A first attempt auto-pauses for pomodoro breaks via the banner, edge-triggered
Decision: _ReviewBanner checks session_manager's isBreak every tick and, for
a first attempt only (problem-backed reviews already get this from
review_store.auto_pause_for_break), pauses on the not-break -> break edge and
resumes on the break -> not-break edge, only if the pause was its own.
Published to /status as autoPaused so the extension shows "Paused (on
pomodoro break)".
Why: break time isn't working time; first attempts were the one review kind
that kept counting through a break. Edge-triggered so a manual Resume during
a break isn't undone a second later, and a manual pause is never auto-resumed.
Cross-reference: carmen-extension needs no change (already renders autoPaused).

[2026-10-05] War-room fixes: one verified patch per bug, sync watermark deferred
Decision: the ten-agent war-room round (see the referee report) produced 54
verified bugs and 62 patches. One patch per bug was applied; second patches
for the same bug were dropped, four patches that collided in api_server.py /
sync_client.py were merged by hand (a hex-color check, topic existence check,
duplicate-name 409 and the sync store lock now coexist), and three bugs with
no patch got small fixes here (screentime.json in the backup, a failed review
save restores its token, review duration capped at 7 days). Two tests needed
fixing for interactions between patches, and the autouse test safety net now
also isolates sync_client's owner/watermark files and the tasks/board files
-- a sync test had written a fake user id into the real private/sync_owner.txt.
Deferred: the sync pull watermark compares against the CLIENT-written
updated_at, so an edit made on a device that was offline is never delivered to
a device that already synced past it. The proper fix is a server-assigned
timestamp column (schema migration on the Supabase project) and pulling on it;
not applied because it changes the deployed database.

[2026-10-09] Desktop wakes the extension with a long-poll instead of waiting for its 7s poll
Decision: GET /events/wait?since=<n> holds the request open (max 25s, at most
4 at once) until state_events' counter moves, which session_manager bumps on
start/end/pause/resume/pomodoro phase/mid-session edits and review_store bumps
whenever its in-progress review changes. Returns {version, changed}; the
extension then asks /status for the real state. Open like /status, nothing but
a counter. The extension keeps its 7s poll as the backstop.
Why: a session started on the desktop while the user sits on a distracting tab
went unnoticed for up to 7s, and the extension can't receive a true push.
Rejected alternative: Chrome native messaging -- needs a host manifest
registered on the machine, much heavier than an open local request.
Rejected alternative: just polling every 1-2s -- constant load for something
that changes a few times a day.
Cross-reference: carmen-extension DESIGN_DECISIONS.txt [2026-10-09].

[2026-10-10] /events/wait evicts the oldest waiter at the cap (max 8) instead of refusing newcomers
Decision: when a ninth request arrives, the oldest parked one is released with
"no change" and the newcomer takes its place. MAX_WAITERS is 8 (was 4).
Why: stress testing showed a refuse-newcomers cap can be starved by requests
whose client already vanished -- an extension background script that restarts
leaves its old request open on the server until the 25s timeout -- locking
live clients out of instant wake-ups until then. Refusing was the wrong side to
protect. The extension also pauses before re-asking after any instant answer,
so eviction cannot turn into a request storm.
Cross-reference: carmen-extension DESIGN_DECISIONS.txt [2026-10-09] (wake loop).

[2026-10-10] A paused session waits behind a new one instead of being ended
Decision: start_session() over a PAUSED session parks it (session_manager's
parkedSessions: full copies of their state, oldest first, any number) instead of filing it as
"superseded". Only one session runs at a time; the parked one has a frozen
clock and enforces nothing. When the running session ends (any way: natural,
manual, nuclear) the most recently parked one comes back as the current session, still
paused, so Resume/End work exactly as they always did. Starting over a
RUNNING session still replaces it. swap_with_parked(parkId) trades places with
any waiting one; end_parked_session(parkId) ends a waiting one without touching
the running one.
Why: pausing a task and starting something else with different restrictions
used to silently destroy the paused task. Automatically coming back as paused
(rather than staying hidden until the user remembers) reuses the one state the
user already understands.
First built with a single waiting slot; changed the same day to any number
because the real use is "a pile of paused things plus the one I'm doing" and a
hard cap just reintroduced the silent-destroy problem at slot two. Order is
last-in-first-out; any waiting one can also be picked by id.
Rejected alternative: letting two sessions run with merged restrictions --
explicitly not wanted.
Review timers linked to a task session follow it: the banner reads its own
session from the parking spot instead of whatever is running (session_manager
state is shared), and its Pause button becomes "Switch to this".
Browser extension: /status carries parkedSessions and the popup lists them with
Switch and End buttons (POST /session/parked/switch and /session/parked/end, token-gated,
body {parkId}; unknown id = 404). Enforcement still follows only the running session.
/status also keeps parkedSession (the first of them) for older readers.
Not covered: a waiting task's already-worked minutes only count toward the
Tasks tab's daily bar once it is ended or back in front.
Cross-reference: carmen-extension DESIGN_DECISIONS.txt [2026-10-10] (waiting sessions in the popup).

[2026-10-10] Sync goes straight to Supabase; the pull cursor is the server's clock
Decision: sync_client no longer talks to sync_server. sync_cloud.py sends the
signed-in user's own access token to Supabase's REST and Storage endpoints, and
row-level security (schema.sql) keeps accounts apart exactly as before. The
rules sync_server enforced in Python moved into one Postgres trigger
(sync_server/migrations/001_direct_sync.sql): an update that isn't newer than
the stored row is ignored, a write stamped >10 minutes ahead of the server
clock is treated as "now", and every accepted write gets server_updated_at from
the server's clock. Pulls ask for server_updated_at > cursor (minus a 30s
overlap) and store the largest value seen, never this device's clock.
Why: the app defaulted to a sync server on 127.0.0.1:8420 that nobody hosts, so
cross-device sync could not work. Hosting a FastAPI proxy only to forward the
same token to Supabase added a bill and a thing to keep running for no security
gain. A client-clock watermark also hid rows: a device with a slow clock stamped
records before another device's last sync time, and that device never pulled
them.
Rejected alternative: host sync_server -- needs an account, costs money,
changes nothing about who can read what.
Rejected alternative: keep both paths -- two transports to test and a watermark
that means different things in each.
Photos: records carry only the file name (descriptionPhotoFile), never an
absolute path; the bytes go to a private bucket, one folder per user, uploaded
before the record that points at them. Names from the cloud are validated
before they touch a path or URL.
Rollout: the SQL migration must be run by hand once, before this code is merged;
until it is, sync probes the database first, writes nothing (no records, no photos)
and reports "needs its one-time setup". Without that guard an upsert would succeed
with no newer-wins check and an old edit could overwrite a newer one in the cloud.
Photos: every local photo a record points at is uploaded once (list kept in
private/uploaded_photos.json), not only photos of records changed this sync.

2026-10-10 -- Quiet taskbar (badges / flashing) during sessions
Choice: flip the two real Windows taskbar settings (TaskbarBadges, TaskbarFlashing)
for the length of the session, instead of hiding the taskbar or muting apps one by
one. Covers every app, and is one registry value each.
Safety: the user value is written to private/taskbar_quiet_saved.json before it is
changed, and put back when the session ends, pauses, hits a pomodoro break, on quit,
and at startup (so a crash cannot leave the taskbar quiet for good).
Per session: stored on the task and on the custom-session dialog (last choice kept),
carried in session state so a waiting session brings its choice back with it.
Not covered yet: calendar-event focus profiles (needs a DB column + sync).
Desktop only; nothing in the extension reads these fields.

2026-10-11 -- Two computers act as one: the running session and session history sync
Choice: the whole session state (running session + every waiting one) is one
cloud row, "live_session", and every finished session is one row,
"session_history", keyed by a sessionId minted at start. Newest change wins by a
stamp in the cloud's clock; each computer learns its own clock error from the
cloud's Date header, so a wrong clock cannot shift when a session ends.
Both computers enforce the shared session (so switching computers changes
nothing); each one's own window facts (browser profile ids) stay local.
Polling: a fast lane polls every ~5 s, always (the other computer cannot know a
session started elsewhere unless it asks). Rejected: Supabase Realtime
websockets -- real-time, but a second connection to keep alive and test, and
5 s is invisible for starting a session; a 3-second session simply never shows
up live on the other computer, only in its history.
Duplicates: both computers may run out the same clock; the entry id is the
sessionId, so history files it once. A newer "nothing running" from the other
computer only ends our session if it names that session as the one it ended;
otherwise ours is kept and re-stamped (two sessions started while apart).
Also shared: a review timed on its own (same newest-wins + "which one ended"
rule as the session), the saved block/allow lists and Start-dialog defaults
(config.SHARED_SETTINGS; window geometry, browser profile ids and the API
token stay per computer), and screen time -- one row per computer per day, each
computer writing only its own, so nothing can conflict; the tab has a button per
computer plus "All computers".
Not shared: browser-only extension sessions (no desktop app involved).
Cross-reference: carmen-extension DESIGN_DECISIONS.txt [2026-10-11] (nothing to
change there: the extension reads whichever session its own desktop has).

2026-10-11 -- Live connection (Realtime) for the fast sync lane, polling as the net
Choice: sync_realtime.py holds a Supabase Realtime websocket and, when it hears
"a sync_records row changed" from ANOTHER device, runs sync_live's ordinary pass
at once. The message carries no data we rely on, so there is one apply path and
a lost message costs nothing. Polling stays as the safety net: every 30 s while
live (or when live is pointless), every 5 s when live is wanted but not working
(blocked network, migration 002 not run), so nothing got slower than before.
Held only when it can help: the account has used a second computer in the last
30 days (multi_device.py: any pulled record carrying another device id), and a
session/review is running or someone touched this computer in the last 5 min.
An idle computer drops the connection and reconnects (with an immediate
catch-up) the moment someone touches it. This keeps a one-computer user off the
connection quota (200 concurrent on Supabase's free plan) and scales better than
polling, whose load grows with every online user.
Rejected: polling every 1-2 s -- 5-10x the requests for a still-not-instant
result, battery and quota cost on every computer, risk of throttling.
Rejected: sending the changed row over the socket and applying it directly -- a
second apply path to keep correct, and nothing gained over one extra GET.
Not verified against the real Supabase: the 1.0.0 message shapes follow the
documented protocol and are covered by a local websocket server in the tests,
but the first real run is the real test.
Cross-reference: carmen-extension DESIGN_DECISIONS.txt [2026-10-11] (no change there).
